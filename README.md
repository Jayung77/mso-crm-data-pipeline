**Tech Stack:** MySQL · HeidiSQL · SQL · Microsoft Excel · Google Sheets  
**Project Type:** 개인 프로젝트 / 합성 의료 MSO 데이터

## 📌 1. 프로젝트 개요 (Overview)

### 프로젝트 배경

의료 MSO(병원경영지원) 환경에서는 고객 기준정보, 예약 상태, 결제 및 미수금 데이터의 정합성이 중요하다.

고객 마스터에 존재하지 않는 거래가 포함되거나, 취소된 예약에 결제 금액이 남아 있는 경우 운영 지표의 정확성이 떨어질 수 있다.

본 프로젝트는 이러한 데이터 품질 문제를 가정하여 **합성 예약·결제 데이터에 오류 9건을 의도적으로 구성하고, SQL 및 Excel로 정제한 후 MySQL에 재적재하여 검증·분석하는 과정**을 수행했다.

실제 환자·병원 데이터가 아닌 포트폴리오용 합성 데이터다.

### 핵심 수행 결과

| 구분 | 결과 |
|---|---|
| 원천 거래 데이터 | 50건 |
| 탐지한 오류 | 9건 |
| 오류 처리 | 3건 제외 + 6건 수정 |
| 정제 후 거래 데이터 | 47건 |
| MySQL 재적재 | HeidiSQL CSV Import · INSERT |
| 정제 후 QA 오류 | **0건** |
| 핵심 KPI 검증 | **7개 항목 모두 PASS** |
| 최종 실수납액 | **13,804,000원** |

### 프로젝트 목표

1. **Data QA:** SQL과 Excel을 활용한 기준정보 불일치 및 금액 이상 탐지
2. **Data Cleansing:** 비즈니스 규칙에 따른 이상 데이터 정제
3. **Data Loading:** 정제된 거래 데이터를 별도 MySQL 테이블로 재적재
4. **Data Validation:** SQL을 이용한 정제 전후 오류 및 KPI 검증
5. **Business Analysis:** 고객 유형·유입 채널별 수납 및 예약 이탈 분석

## 🗄️ 3. 데이터 구조 및 처리 흐름

### 주요 테이블

| 테이블 | 데이터 규모 | 역할 |
|---|---:|---|
| `customer_master` | 20건 | 고객 차트번호 및 등급 등 기준정보 |
| `crm_transaction_log` | 50건 | 의도적 오류가 포함된 원천 거래 데이터 |
| `crm_transaction_clean` | 47건 | 정제 후 재적재한 최종 분석 데이터 |

고객 마스터와 거래 데이터는 `Chart_No`를 기준으로 연결했다.

원천 데이터에 마스터 미등록 거래 3건을 포함해 SQL `LEFT JOIN`으로 참조 불일치를 탐지할 수 있도록 구성했다.

QA 실습을 위해 원천 거래 테이블에는 해당 오류의 입력을 막는 FK 및 금액 CHECK 제약을 적용하지 않았다.

### 데이터 처리 흐름

**MySQL 원천 데이터 생성 (50건)**  
↓  
**SQL 오류 탐지 (9건)**  
↓  
**Excel 정제 (3건 제외, 6건 수정)**  
↓  
**CSV UTF-8 저장 (47건)**  
↓  
**HeidiSQL을 이용한 MySQL 재적재**  
↓  
**SQL 정합성 재검증 (오류 0건, KPI 7개 PASS)**  
↓  
**Google Sheets 운영 KPI 분석**

원천 테이블을 보존하고 정제 데이터를 별도 테이블로 적재해 정제 전후 비교가 가능하도록 했다.

## 🔍 4. 데이터 품질 검증 및 정제 (Data QA)

원천 데이터 50건에서 총 **9건의 의도적 오류**를 탐지했다.

| 검증 유형 | 오류 내용 | 건수 | 처리 방식 |
|---|---|---:|---|
| QA-01 고객 마스터 불일치 | 미등록 차트번호 존재 | 3건 | 분석 대상 제외 |
| QA-02 예약 상태·금액 모순 | 노쇼·취소 상태에 수납액 또는 미수금 잔존 | 5건 | 금액 0원 보정 |
| QA-03 음수 미수금 | 미수금 -20,000원 발생 | 1건 | 미수금 0원 보정 |
| **합계** | | **9건** | |

### SQL 기반 오류 탐지

- `LEFT JOIN`: 고객 마스터 미등록 차트번호 탐지
- `WHERE`: 예약 상태와 금액 간 논리적 불일치 확인
- 금액 조건식: 음수 미수금 및 이상 거래 식별

### Excel 기반 정제

- `VLOOKUP`으로 고객 기준정보 일치 여부 확인
- `IF`, `AND`, `OR`로 예약 상태·금액 검증
- 마스터 불일치 거래 3건 제외
- 결제정보 모순 5건 및 음수 미수금 1건 수정

**최종 정제 결과: 50건 → 47건**

※ 노쇼·예약취소 금액을 0원으로 수정한 것은 본 합성 데이터에 정의한 규칙이다. 실제 운영 환경에서는 예약금, 환불 및 취소 수수료 정책을 별도로 확인해야 한다.

## 🔄 5. MySQL 정제 데이터 재적재 (Data Loading)

Excel에서 정제한 데이터를 CSV로 저장한 뒤 **HeidiSQL의 CSV Import 기능을 사용하여 MySQL에 재적재**했다.

### STEP 1. 원천 데이터 추출 및 정제

- MySQL 원천 테이블 `crm_transaction_log`에서 거래 데이터 50건 추출
- SQL 및 Excel을 이용한 오류 검증
- 마스터 미등록 3건 제외, 금액 오류 6건 수정
- 정제된 거래 데이터 47건 확보

### STEP 2. CSV 파일 생성

정제 데이터의 거래 컬럼 10개를 CSV 형식으로 저장했다.

| 항목 | 설정 |
|---|---|
| 파일명 | `crm_transaction_clean.csv` |
| 데이터 | 47건 |
| 컬럼 | 10개 |
| 파일 형식 | CSV |
| 인코딩 | UTF-8 |
| 첫 번째 행 | 컬럼명(Header) |

[정제 완료 CSV 파일 확인](crm_transaction_clean.csv)

### STEP 3. 별도 MySQL 테이블 생성

원천 데이터를 보존하기 위해 동일한 컬럼 구조의 정제 테이블을 생성했다.

```sql
CREATE TABLE practice.crm_transaction_clean
LIKE practice.crm_transaction_log;
```

`crm_transaction_log`에는 정제 전 데이터 50건을 유지하고, `crm_transaction_clean`에는 정제된 47건을 적재했다.

### STEP 4. HeidiSQL CSV Import

| 적재 항목 | 적용 설정 |
|---|---|
| 대상 테이블 | `practice.crm_transaction_clean` |
| 입력 데이터 | `crm_transaction_clean.csv` |
| 인코딩 | `utf8mb4` |
| 필드 구분자 | 쉼표(`,`) |
| 헤더 처리 | 첫 행 건너뛰기 |
| 적재 방식 | `INSERT` |
| 파일 처리 | 클라이언트 측 CSV 분석 |

초기 파일 적재 과정에서 서버의 `LOCAL INFILE` 제한으로 오류가 발생했다.

이에 HeidiSQL의 클라이언트 측 CSV Import 방식을 사용하여 정제 데이터를 적재했다.

### STEP 5. 적재 후 SQL 검증

정제 테이블에 재적재한 후 `COUNT`, `SUM`, `CASE WHEN`, `LEFT JOIN`을 활용하여 데이터 건수, 오류 잔존 여부 및 KPI 집계 결과를 검증했다.

검증 SQL: [03_clean_data_validation.sql](03_clean_data_validation.sql)

- 신환·구환은 거래별 `Is_First_Visit` 기록값을 기준으로 집계했다.
- 채널별 수납 및 이탈률은 해당 표본에서 관찰된 결과로, 일반적인 의료기관 성과를 의미하지 않는다.
- 예약금 및 예약 확인 절차의 개선 효과는 실제로 검증되지 않았다.
- 데이터 정제와 재적재는 Excel 수동 검수 및 HeidiSQL CSV Import 방식으로 수행했다.
- 자동화된 ETL 파이프라인과 실제 의료기관의 운영 시스템을 구축한 것은 아니다.
